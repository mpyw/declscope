# CLAUDE.md

This file provides guidance to Claude Code when working with code in this repository.

## Project overview

**declscope** is a Go linter that adds a pseudo visibility level below `unexported`, and a real one for methods and struct fields, and enforces them with [`go/analysis`](https://pkg.go.dev/golang.org/x/tools/go/analysis). It exists so that a package can stay **flat** without losing every internal boundary.

| Scope | Meaning |
| --- | --- |
| `package` | Usable anywhere in the package — what Go's unexported already means |
| `private` | Usable only inside its own **namespace** |

**Exportedness decides the default and nothing else.** An exported declaration resolves to `package` — no boundary — unless a directive gives it one. Do not reach for "is it reachable from outside the package": a single-package analysis cannot answer it, since a type escapes through an exported signature, an embedding, an alias, or an interface it satisfies, and an earlier attempt to guess reported boundaries on API every importer reaches. What the author knows, the author states: a directive binds whatever it reaches, exported or not, which is how a DTO capitalized for a serializer is protected. A use outside the package is never analyzed, so `public` would be a level nothing could check; there is no `defaults.exported`, and adding one back means claiming an enforcement the analysis cannot perform. `package main` is not an exception either: `-buildmode=plugin` makes its exported symbols reachable by name from another program (verified by building one and looking the symbol up), so applying `defaults.unexported` to them would report a boundary on every plugin's surface.

**`declscope shrink` is the one place exportedness changes, and it is not the analyzer.** Inside `internal/`, Go limits the importers to one directory tree, so a run that loads the whole module sees every one of them and the absence of a use becomes evidence. `shrink` reports an exported declaration nothing outside its package uses (`rule.Overexported`) and unexports it. It is a subcommand driving `go/packages`, like `baseline`: the analyzer stays single-package, and there is no config key, since `go vet` and golangci-lint would read one and silently do nothing. The two principles above still hold for the analyzer. The exception is stated here so that nobody widens it: outside `internal/`, or wherever an importer could be unseen, nothing is said. `spec/shrink.fsl` is the model, and #112 is the design record.

- **The report and the fix are held to different standards.** The report may be wrong where a use is possible but not provable. The fix is made only where no use can exist. Every doubt withholds the fix and keeps the report, the rename rule again.
- **A method or field of an internal type can be used from another module.** `pub.Get().Method()` needs no import of the type, and `pub.Get().Inner` names an embedded type as a field. `evidenceExposure` walks the exported API of every package a module this run does not load may import, and a member or embedded type it reaches is not reported. The original design missed this, and `SilentWhenExposed` in the spec pins it. The roots are the packages `rangeOf` cannot vouch for, **not** the packages with no `internal` element in their path: a package under an `internal/` whose parent lies above the module hands values out to another module just the same (the review of the first version reproduced this, `testdata/outer`).
- **Conversions into interfaces come from SSA's `MakeInterface`, not a fork of `refactor/satisfy`.** satisfy skips empty interfaces, which is exactly the `fmt`/`json`/`reflect` case, and forking it drags in `x/tools/internal/typeparams`. SSA reports every conversion, with module generics instantiated. A generic declared outside the module has no body, so every type argument given to one is taken to escape. satisfy stays for static satisfaction, including type assertions, which SSA does not model as conversions. SSA drops `var _ I = T{}` and dead function literals: no value is made at run time, so nothing escapes, and the fix is sound there.
- **The escape closure follows containment.** `json.Marshal([]T{})` reads `T`'s fields, so fields, elements, keys, pointees, and method and function signatures are walked. An instantiation is walked through its origin and its type arguments, or a recursive generic type expands without end.
- **Deletion is out of scope.** Once unexported, a declaration nothing uses is U1000's and gopls `unusedfunc`'s. Deleting would need a fixpoint over clusters, iota gaps and initializer side effects. Unexporting changes no reference, so one pass converges. cristian-sima/deadexports deletes, and in a test it broke a `GOOS=windows` build and deleted a generic `String()` method.
- **A bare `//declscope:ignore` does not reach `overexported`** (`directive.Ignore.Covers`), and the analyzer never judges an ignore naming it (`NamesModuleWide`). Otherwise the analyzer would call an ignore unused that only `shrink` needed. `shrink` judges an ignore naming only `overexported`. One naming another rule as well is judged by neither side.
- **A member is named alone in the message.** Its type may be fixed in the same run, and a report the run keeps must read the same afterwards. The convergence test caught `List.Len` turning into `list.Len`. For the same reason, a name another fix claimed reads as taken, not as a separate reason.
- **Example functions name declarations textually.** `go vet` checks that `ExampleF` still names `F`, and the convergence test caught the rename breaking it. An example in the package withholds the fix, and one in the external test package is a use by external tests.
- **Declarations are keyed by position (`keyOf`), not by object.** A package with tests is type-checked more than once, with separate objects per variant, and the variants share the parsed files.
- **A package whose files the build excludes entirely is not in the load at all.** `loadExcluded` walks the module directory instead of reading `IgnoredFiles`, and records nested modules on the way.
- **A nested module is recorded by its module path, and looked for before any directory is skipped.** Go checks `internal/` by import path, so one in `_tools/` or `testdata/` whose path extends an `internal/` parent can import the package, and one with an unrelated path cannot, wherever it sits. Keying it by directory both missed `_tools/` and would have unjudged declscope's own `internal/` over its `testdata` modules.
- **Dependencies come from export data (no `NeedDeps`).** Loading them from source type-checked and built SSA for the whole standard library: on declscope itself 415 MB and 1.1 s against 78 MB and 0.7 s. A generic declared outside the module has no body either way, which `evidenceInstances` covers.
- **The rename is asked only once a report stands.** It claims its new name for the rest of the run, so a silenced declaration asking first withheld another's fix for nothing.
- **Positions ignore `//line` (`PositionFor(pos, false)`).** A `//line` directive would otherwise key a declaration by another file's name and send `Apply` to it.
- **A linkname target spells a method as `T.M` or `(*T).M`, and both spell `T`.**

A second review found seven more holes, pinned by `testdata/review2` and `testdata/deep`:

- **The walk goes into every directory for go.mod files**, and only stops reading Go files where `./...` does. Skipping `testdata/` outright missed `testdata/tools/go.mod`.
- **A package with assembly for any architecture is skipped.** Assembly for another `GOARCH` lands in `IgnoredFiles`, not `OtherFiles`, and names symbols in a build this run does not see.
- **Escape is recorded per field, not only per type.** `type Wire Record` shares `Record`'s field objects, so `json.Marshal(Wire(r))` exposes them under either name, and keying by the owner silently dropped JSON fields.
- **Members reserve their new name per package, not per owner, and a type reserves the member name too.** `A.ID` and `B.Id` both lower to `id`, and a type embedding both would hold an ambiguous selector. An embedded field takes its type's name, so types and members share that reservation.
- **An unnamed struct promotes members too**, so the member guard walks `facts.structs` as well as `facts.named`.
- **package main is always an exposure root**, inside `internal/` or not. A plugin host looks its exported variables up.
- **The unused report on an ignore naming overexported is answered as the analyzer answers its own**: by a sibling naming `unused`, or by a file-level ignore covering `unused`. The analyzer in turn skips judging such an answer (`answersModuleWide` in ignore.go), because it cannot see the report it answers. Without both halves, one directive meant two different things to the two tools.
- **Unnamed structs are collected from inside every expression's type**, and kept once per identity. One in a parameter of a dependency loaded from export data appears only inside the type of the expression naming the function. No fixture reproduces that case, since it needs a dependency outside the module.
- **The one unchecked assumption is in the README.** Every module whose path extends an `internal/` parent is taken to live under that parent's directory. Go checks `internal/` by import path, so a `/v2` published from another branch could import the package unseen.

**A receiver-ignoring method is a way to dodge the naming rule, and golangci-lint closes it.** Methods are exempt from `qualify` because a method is never read bare. Writing a free helper as a method whose body never names its receiver takes that exemption without earning it, and it happened here once already. `revive`'s `unused-receiver` is enabled for exactly this; declscope has no business knowing about the shape. Do not add a receiver to silence the rule.

**Members and methods are not one thing.** A member is written *inside* its type's declaration: a struct field, and an interface's method name. Its file is where the type is, not a binding we chose, so the type's directive contains it the way a `var (...)` block contains its specs. A method with a receiver is an ordinary top-level declaration — its file gives it its namespace, and nothing above it reaches it. Binding methods to their type's file instead made a method unusable from the file that wrote it, with no scope able to express what the author meant. Encapsulation never rested on it: a method reaching another namespace's private member is caught by the **member**. Satisfying an interface is not a use of its method names, and counting it as one would make the sealed-interface idiom a violation everywhere, repairable only by a directive that changes nothing about Go semantics.

### Core concept: reach is stated, ownership is named

The single most important thing to understand before changing anything here is that **the name never determines reach**.

Everything unexported is private to its namespace unless a directive or `defaults.unexported` widens it; a **name** never does. A namespace prefix must never mean package-internal: that overloads one signal with two meanings, so a prefix added purely for legibility would silently widen a declaration, and a codebase that prefixed everything for readability would end up with nothing protected. The same separation is what keeps a boundary crossing from ever having a rename fix, and a diagnostic from ever carrying two conflicting alternatives.

The namespace in a name does a separate job: it is an **ownership mark** on package-level declarations, making the owning unit legible at every use site. The rule asks the name to carry the namespace *somewhere*, starting at a word boundary (`namespace.Contains`), and the fix prefixes it. Demanding a prefix was tried and rejected: Go puts a type's category last (`statementReducer`) and spells a constructor `NewTracer`, so the demand produced `reducerStatementReducer` and `TracerNewTracer` — over six repositories, one qualify diagnostic in eight doubled a word the name already carried. The rule applies to unexported declarations, and to exported ones when `rules.naming.exported` is on — inside the package an exported name is read as bare as any other, so the package qualifier that explains an external use is absent exactly where the mark is wanted. A rename keeps exportedness (`Load` → `UserLoad`): one that quietly unexported a declaration would delete the API to satisfy a linter. An exported rename is never *offered*, only reported, since the uses outside the package cannot be seen.

`rules.naming` holds the naming rule plus `exported`, which widens it, and `vocabulary`, which widens what counts as carrying the namespace without touching when it is asked. `exported` is the one deliberate cross-cutting key and it **broadens** what is reported. A cross-cutting key that switches reporting *off* — a `members: false` gating the collection of methods and fields — is the shape to avoid: it silences more than its name suggests.

`rules.boundary: off` is not that shape. It switches one rule off, the way `rules.surplus: off` does, and it exists for the repository that wants the ownership mark in a name without the scope behind it. **It must not be made to switch `surplus` as well.** Turning boundary off does leave `surplus` auditing directives that no longer do a job, and the README says to set `surplus: off` alongside it, but coupling them in code is exactly the key that silences more than its name says. Two keys, each doing what it is called.

`boundary: off` is also not the way to adopt declscope gradually, and the README says so where it is documented. A baseline records what a codebase already has and still reports what is new; a switch reports nothing, and the cost of turning it on is never measured. Do not recommend it for adoption.

`rules.naming.qualify` reads a `rule.QualifyMode` — `Always`, `Never` or `OnDemand` — and `QualifyMode.Applies` is the predicate it gates on. **It defaults to `never`: the naming rule is opt-in.** It shipped as `ondemand` first, and measurement rejected that. Naming findings did not correlate with encapsulation problems (measured on the containment rule at v0.1: goroutinectx 0 boundary vs 22 naming, gormreuse 11 vs 38, zerologlintctx 3 vs 20, suve 749 vs 650), whether a prefixed name reads as a noun phrase or an imperative depends on the file name's part of speech, which the tool cannot see (`collectAddFunc` vs `commentsAttached`), and the containment test leans on English spelling. Do not make it the default again on the strength of any one repository. Under `ondemand` it requires the mark only once a package has a second namespace; in a package with one, every other rule is structurally inert anyway. QualifyMode declares the values it accepts as a `rule.QualifyModeSet`, so a rejected value is answered with what that setting accepts, and `QualifyMode.String()` returns the same spelling the config takes.

`rules.naming.exported` is a plain boolean, defaulting to `false`.

`filter` replaced `exclude`, which could only subtract. `only` narrows and `omit` takes back out, each list matching on **any** of its patterns, and an empty `only` places no restriction rather than matching nothing — that asymmetry is a rule, not a consequence, and `spec/filter.fsl` pins it. The two are applied in the order the config reads, and the order is not a choice: both lists ask about one path, so the two readings name the same set. Do not add a key that reverses them. `exclude` is gone rather than aliased, so a stale config gets the unknown-key error naming what the section takes, exactly as `rules.naming.unqualify` does.

Config files **compose**, and each key composes on its own. `FindChain` returns every file between the package and the module root, outermost first, and `Apply` runs them in that order: a key a file states wins, a key it does not state is left as the file above set it, which the `boolSetting.set` pattern already gave for free. `baseline` always worked this way — it has its own upward search — so the chain makes one key's behaviour the rule. An explicit `-config` builds no chain: the caller named the rules to use.

`rules.naming.vocabulary` merges per namespace rather than the nearer map replacing it, since adding one word should not cost restating the rest. `filter` is the one place the composition is not "nearest wins": `only` intersects and `omit` unions, which is `spec/filter_chain.fsl`'s subject. **The property that buys is that a config file can only ever shrink what is read**, so an `omit` at the root holds everywhere below it. Do not add a key that lets a nested file widen — `inherit: false` was considered and rejected for exactly that, because a single escape hatch turns the guarantee into "unless somebody used it". `MonotoneDown` is what a change in that direction breaks.

Because the chain holds patterns from several depths, a pattern travels with the directory it was written in (`internal.FilterPattern`), and `Only` is a slice of groups rather than a flat list. Flattening would lose which base each pattern anchors to, and intersecting would become impossible.

`rules.naming.vocabulary` maps a namespace to extra words that carry it (`mouse: [wheel]`, `index: [indices]`). A listed word goes through `namespace.Contains` exactly as the namespace does — word boundary on the left, free right edge — so it is a spelling, never a scope, and never a semantic "related words" guess: explicit enumeration was chosen over any automatic relatedness, which cannot be audited. A namespace needing a long list is a design smell, and the README says so.

There is no `unqualify` rule any more. It forbade the prefix where `qualify` did not require it, and the containment relaxation removed its meaning: once any position in the name counts, there is no single word to drop (`LoadConfig` minus `config` leaves `Load`), and it had fired 24 times against qualify's 1345 over the same six repositories. Do not add a compatibility shim for it: `rules.naming.unqualify` now fails as an unknown key through the strict YAML decoding, and `//declscope:ignore unqualify` as an unknown rule through `rule.Parse` — both are the loud failure a stale config should get.

A file marked `//declscope:core` joins the package's core namespace, whose prefix is empty, so the naming rule skips it. Several files may share the core; `core` and `namespace` on one file conflict, since a core file's namespace *is* the core.

**Members are exempt from the naming rule.** They are already namespaced by the type that owns them and cannot collide, so a prefix would produce `u.userSave()`, exactly the stutter Go idiom avoids. Their problem is encapsulation, not naming, and a member violation is never fixed by renaming.

Scope resolution is shared: `collection.bind` (`internal/scopesite.go`) serves every kind, so that `defaults.unexported`, the file-level directive and the declaration's own govern every declaration in a package. A **field** takes one extra step first, from the type that contains it; a method takes none. A knob that works on some declarations and not others is the shape to avoid.

### Namespaces

A namespace is the unit of privacy, defaulting to the camelCased file name so that each file is its own namespace, and overridable with `//declscope:namespace <name>` before the package clause.

The namespace count that `rules.naming.qualify: ondemand` keys off is taken from the package's **non-test** files (`collection.namespaces`). A test file joins its subject's namespace rather than creating a boundary, and counting one whose name matches no source file (`integration_test.go`) would make a package's test variant disagree with the package itself.

The indirection is deliberate: using the file name *itself* would mean renaming a file cascades into renaming every identifier it declares. It also makes `_test.go` sharing its subject's namespace fall out naturally rather than needing a special case.

**A `//declscope:namespace` that restates the name the file derives is not reported.** The check would be sound. `namespace.Of` reads no configuration, so the comparison cannot be flipped by a line of YAML. It stays out for the other half of the inert test's reason. Such a directive may be pinning the namespace against a future file rename, and it is the only way an author can say that. Reporting it would ask the author to delete the thing doing that job. The only escape would be `//declscope:ignore unused` on the whole file, which silences more than the one report. This is the close of #99.

Normalization rules live in `internal/namespace` and are covered by a table test. GOOS/GOARCH suffixes are stripped because they are build constraints, not namespaces. Every run of non-identifier characters is a separator (`foo-bar.go` → `fooBar`), a PascalCase stem is lowered (`Foo.go` → `foo`), and an initialism in a later segment is spelled the way Go spells it (`user_id.go` → `userID`) using golint's `commonInitialisms` list, vendored rather than pulled in as a dependency.

**A namespace is an identity first and a prefix second, and the two are kept apart.** `namespace.Of` always returns the normalized stem — `2fa.go` yields `2fa` — so that `fileInfo.key()` never falls back to the file path and `2fa_test.go` shares its subject's namespace like every other test. `namespace.CanPrefix` separately says whether that stem can be prepended to an unexported identifier; `checkQualify` gates on it and stays silent when it is false, because the alternative is suggesting `2faTotp` or `FooBar` — containment alone could be satisfied there, but the fix could not be, and the rule stays out rather than report what it cannot remedy. Returning `""` from `Of` for a digit-leading stem would lose the identity in order to protect the prefix; the second job must never kill the first.

`namespace.Contains` is what the rule gates on: the namespace may sit anywhere in the name, **ignoring case**, as long as its left edge opens a word — `statementReducer` carries `reducer`, `APIParser` carries `parser`. The right edge is deliberately free, so a plural or an agent noun still counts (`users` carries `user`); the cost is a name that merely opens with the namespace (`mode` found in `models`), which is the narrower failure than `key` found in `monkey` if the left edge were free too. Two inflections change the namespace's own spelling and are matched through forms generated from the namespace (`inflections`): a final e dropped before -ing (`store` → `storing`) and y → i (`apply` → `applies`/`applied`). **Never stem the name side instead**: matching a `stor` stem with the free right edge accepts `story` and `storm`, which is why only whole generated forms are compared — the unit tests pin `story`/`storm`/`appliance` as rejected. Only the final word of a compound namespace inflects, so inspecting the last two runes suffices. `namespace.HasPrefix` remains as the stricter both-edges test for the exact shape the fix produces; `Qualify` spells the first word of the name the way Go spells an initialism (`id` → `userID`) and no-ops on a name that already carries the namespace.

## Architecture

```text
analyzer.go               Analyzer definition, -config flag, config discovery
internal/
  analyzer.go             core. Run: collect files -> targets -> refs -> report
  subject.go              core. The model every stage shares: fileInfo, target,
                          ref, kind, the index over them, and the problem sink
  collect.go              builds the index: files, targets, references
  options.go              resolved configuration: the booleans and the filter globs
  scopesite.go            scope resolution (bind), which directives bound nothing,
                          and strict's redundant directives with the fix deleting them
  report.go               diagnostics and suggested fixes
  survey.go               the same findings, with what became of each, plus
                          the crossings the report never names
  ignore.go               ignore accounting: which comment silenced what, and which bound to nothing
  rename.go               the conditions under which a rename fix is offered at all
  surplus.go              the surplus rule: the judgment, the reach evidence it is
                          made from, and strict's per-declaration findings
  rule/                   the rule vocabulary, shared by diagnostics, config, baseline and ignores.
                          rule.go is its core; mode.go holds QualifyMode, BoundaryMode,
                          SurplusMode and UnusedMode, the vocabularies each rule's
                          setting is spelled in
  namespace/              file name -> namespace, containment matching, qualify
  scope/                  the two-level Scope enum
  directive/              //declscope:... comment parsing, and the names that
                          //go:linkname and //export bind
  config/                 YAML loading and lookup
  baseline/               baseline file format, lookup and regeneration
  measure/                what survey and inspect report: the model, the folds
                          over it, and the text, JSON and markdown renderers
  shrink/                 declscope shrink: loads the whole module and judges
                          exportedness inside internal/. shrink.go is its core,
                          load.go the module and its build-excluded files,
                          evidence.go who uses what, rename.go the unexport
cmd/declscope/            singlechecker entry point, the `baseline`, `survey`,
                          `inspect` and `shrink` subcommands, and -V
```

Each file of `internal/` is its own namespace, taken from its stem. `analyzer.go` and `subject.go` join the **core** instead: the model they hold is read by every stage, and in a named namespace each type would have to carry that namespace's prefix, so the builder's name would be spelled into the model every other file reads.

Each stage's own working state is embedded into `collection` from a struct
declared in the file that owns it: `ignoreBook`, `scopesiteBook`, `collectBook`,
`renameBook`, `surplusBook`. The type carries `//declscope:package` so the core can embed it,
and the field carries `//declscope:private` to narrow itself back — the type's
directive would otherwise reach the field and undo the point. Embedding rather
than nesting keeps the call sites spelling `c.ignores`, and reaching one from
the wrong stage is a boundary crossing.

The maps are filled on first use by the owning file, so the constructor in
collect.go never writes another stage's state. `//declscope:package` on a
constructor would have worked too, but the lazy form is what rename.go already
did.

`subject.go` carries a file-level `//declscope:package` because the shared model is shared on purpose. Everything else that crosses a namespace says so one declaration at a time, and those directives are the record of what each stage hands to another. `cmd/declscope/baseline.go`, `survey.go`, `inspect.go`, `load.go` and `version.go` are each their own namespace for the same reason; only `main.go` is `main`.

`internal/measure` repeats the shape one level down. `model.go` is its core, because every renderer reads the model and a named namespace would spell itself into each type's name; it states no scope, since everything in it is exported and already package-scoped. `cell.go` and `sink.go` carry file-level directives because they exist to be shared — the same exception `subject.go` takes. Each renderer is its own namespace, one per format rather than one per format and type, and reaches the model through `WriteFormat`, which is the only entry a caller outside the package has.

> [!IMPORTANT]
> Keep those directives when adding files to either unit. Without them the naming rule asks every declaration to carry a `baseline`/`analyzer` prefix, which is the tool reporting a boundary that is not really there.

### Structural constraints

- Everything is checked **within a single package**. Namespaces are therefore implicitly package-qualified; `pass.Pkg` scoping does that for free and no `analysis.Fact` is needed.
- Whether an *exported* identifier is used outside its package is deliberately **out of scope**: `go/analysis` has no upward view of the program. Answering it would require a separate whole-program mode driven by `packages.Load`, which would not fit a plain Analyzer. Combine with an unused-code linter instead.
- Generated files are excluded as declaration sites **and** as reference sites, since a violation in generated code is not actionable.

### Reference collection

`collectRefs` is where every rule gets its evidence, and two facts about `go/types` shape it:

- **An ident can be a definition and a use at once.** An embedded field's ident is in `Defs` as the field `Var` *and* in `Uses` as the `TypeName`. `Defs` and `Uses` are therefore consulted independently; returning after a hit in `Defs` would drop the type use and with it both a rename edit and a `boundary` diagnostic. The embedded field itself is deliberately **not** a target (`addFields` skips it) — it has no name of its own to hide or prefix — but a selection through it (`u.count`) is spelled with the type's name, so `embeddedTypeName` adds those idents to the type's rename set. Aliases are kept as aliases there: a field embedding `A` is spelled `A`, whatever `A` denotes.
- **`Uses` records the instantiated member of a generic type**, for a selection on `List[int]` and even on `List[T]` inside `List`'s own methods, while `byObj` is keyed by the declared object. Every object taken from `Uses` goes through `origin()` (`(*types.Var).Origin()` / `(*types.Func).Origin()`) before the lookup and before it joins `idents`. Without that, every field and method of a generic type would be silently unchecked. The same holds for a field read off an instantiated struct type rather than an ident: an unkeyed literal's (`collectUnkeyedFields`) and a struct conversion's (`surplusConversions`) go through `origin()` too. Only a field whose type mentions a type parameter is a new object in the instantiation, so a fixture for this needs such a field. `receiver` needs no such step: `(*types.Named).Obj()` already names the origin's type name.

`testdata/src/generics`, `embedded` and `fixembedded` pin both, including the receiver resolution of a method on `List[T]`. `unkeyed`, `surplusconvert` and `surplusstrictreach` pin the literal and the conversion of an instantiation.

## Rules

`internal/rule` holds the one vocabulary. The same name is the diagnostic's `Category`, the `Rule` field of a baseline key, and what an ignore directive targets. **Adding a rule means adding it there**, not inventing a string at the report site.

| Rule | Reports | Fix |
| --- | --- | --- |
| `boundary` | A declaration used from outside the namespace it is private to | Insert `//declscope:package`, unless the **declaration's own** directive states the scope |
| `qualify` | A package-level declaration whose name does not carry its namespace | Rename via `namespace.Qualify`, when provably safe and not exported |
| `surplus` | Package scope wider than any use visible to declscope. `rules.surplus: loose` (the default) reports a `//declscope:package` none of whose dependents is reached; `strict` also reports each unreached dependent of a directive otherwise in use; `off` reports nothing | None under `loose` — a false positive would be an automatic edit deleting a load-bearing directive. Under `strict`, insert `//declscope:private` on the dependent |
| `unused` | A directive that decides nothing: an ignore that silenced nothing, or a scope directive that binds nothing. `rules.unused: strict` also reports a scope directive naming the scope everything it reaches would have without it under the configuration in force; `off` reports nothing | None under `loose`. Under `strict`, delete the redundant directive |
| `directive` | A directive that is malformed, unknown, conflicting or misplaced. It has no configuration key and is always on | None |
| `overexported` | An exported declaration of an `internal/` package that nothing outside its package uses. Only `declscope shrink` reports it, and it is not in `rule.All` | Unexport it, when no doubt remains |

The config key is `rules.surplus`, the rule's own name, and it takes a mode: `off`, `loose` or `strict`. A boolean key would have had to be named for what it switches (`allowSurplus`), since `surplus: true` reads as "surplus: yes please". A mode has no such reading, so the rule's name, its diagnostic category, its baseline key, its `//declscope:ignore` target and its configuration key are all one word. `rules.boundary` takes `off` or `on` for the same reason: it was `allowBoundary: bool` until the surplus key showed the shape, and now no key differs from its rule's name. `rules.unused` is the unused rule's; the `directive` and `filter` rules have no key.

`allowSurplus` and `allowBoundary` are refused, not aliased, the way `exclude` and `rules.naming.unqualify` went: a stale config fails through the strict YAML decoding as an unknown key, and the message names what `rules` takes. That break is accepted because it is loud and tells the reader what to write. A silent change in what gets reported would be neither.

**The default is `loose`, and `strict` is opt-in: an upgrade must not add reports to a repository whose config did not change.** That is the whole reason, and it holds whatever `strict` measures. `loose` itself defaulting on was measured rather than assumed: across eight repositories, including declscope itself with 43 directives, turning it on changes no diagnostic count. declscope holds itself to `strict` in `.declscope-strict.yaml`.

`rule.SurplusMode` is a sibling of `rule.QualifyMode` rather than three more `QualifyMode` values, `rule.BoundaryMode` a third sibling with two, and `rule.UnusedMode` a fourth with `off`, `loose` and `strict`. `QualifyMode` carries `Applies(namespaces)`, a question about how many namespaces a package has, which means nothing for this rule, and a `QualifyMode` that could hold `loose` would still need an answer to it. **Each mode type is named for the rule it belongs to.** A bare `Mode` read as a shared vocabulary while holding `ondemand`, which only the naming rule means. The shape is the same (`SurplusModeSet.Parse`, the accepted-values error, `String()` round-tripping the config spelling), and the part they share, spelling "a, b or c", is `modeJoin`. They live in `internal/rule` beside the rule names, because a mode is how one rule is configured, which is part of that rule's vocabulary. `rule.go` joins the core so that the names every caller spells stay `rule.Boundary`, not `rule.RuleBoundary`.

**`surplus` (internal/surplus.go) concludes from an absence, and every design choice there is about not being wrong.** `spec/surplus.fsl` is the model; `NeverReportsReachable` is the property. The judgment is **per physical directive**, grouped by `target.boundBy.ScopePos`: the advice is to delete the comment, which is only safe when nothing whose scope comes from it is reached, and a declaration stating its own scope depends on no outer directive. The whole comment stays quiet when any dependent is exported (importers reach it invisibly), spelled from another namespace (`c.refs`, so unkeyed literals and generic selections count), in an interface contract of the package, carried by an exported type or alias (full method sets, promoted methods included), paired by a struct conversion, or named by `//go:linkname`/`//export`. Interfaces and satisfiers are collected from `TypesInfo.Types` (values included), `TypesInfo.Instances` and `Defs` — **never from package scope alone**, which misses anonymous interfaces, function-local types and instantiations; the interface lookup passes `addressable=true` for pointer-receiver promotion and goes through `Origin()` for instantiated methods, and a requirement found on its own interface (`fn == want`) is skipped so interface members stay reportable. `surplusSeesEveryFile` switches the rule off for the whole package on any unread reference site: unseen in-package tests or build-excluded files (`unseen`), generated or filtered-out files, cgo, assembly (`pass.OtherFiles`/`IgnoredFiles`). A directive on a field that restates its type's is **inert** and already reported by the unused-scope check, so fixtures for "the member does not depend on the type's directive" use `//declscope:private` on the member, not a redundant `package`.

### `strict`

**`loose` judges a directive as a whole, so a directive with one reached dependent says nothing about the others.** A file-level `//declscope:package` over `helperA`, called from another namespace, and `helperB`, which is not, reports nothing under `loose`. The same holds one level down for a type's fields and one level across for a block's specs. `strict` reports each such dependent on its own, and offers `//declscope:private` on it. It is the same rule and the same name, so `//declscope:ignore surplus` silences both shapes and a baseline records both under `surplus`. The two never share a baseline key: `loose` keys the directive by its first dependent, which belongs to a condemned directive, and `strict` only reports under a directive that is not condemned.

**It shares `loose`'s soundness argument by sharing its code.** Both conclude from an absence, so `strict` must never call a declaration unreached that `loose` would count as reached. `surplusState.reachesOutside` is the one test, over the one evidence (`c.refs`, conversions, satisfactions, exported carriers, linknames), behind `surplusSeesEveryFile`, and `surplusJudged` computes it once without reading the mode. The evidence itself is gathered on the first `reachesOutside` call, not up front: interface satisfaction is the costly part, and a package with no `//declscope:package` asks nothing under `loose`. **Do not copy the checks into a second function** — two copies of "is this reached" is how one of them falls behind the next reach path someone adds. `spec/surplus_strict.fsl` is the model, `NeverReportsReachable` covers both shapes, and `NeverTwiceOnOneDeclaration` pins that `strict` adds to `loose` without repeating it.

Which directive a declaration depends on is `bindAtScopeSite`'s answer (`boundAt`, `boundBy`), never a second resolution. A spec whose block wrote the directive is `boundAt == Decl` there, because `Decl.Merge` folds the block's into the spec's own; `target.fromBlock` is recorded at the merge, the only place the difference is still known.

What it reports, and each decision behind it:

- **Only when an enclosing directive is what widened the declaration**: the type's, the block's or the file's, not its own, not exportedness ("Exportedness decides the default and nothing else"), and only while `defaults.unexported` is `private`. That last test reads the configuration, which the unused rule's `loose` binding test deliberately does not. The two questions differ: `bind`'s quantifier decides whether a *comment* is unused under every configuration, because the comment outlives any one of them. `strict` asks whether the directive widened the declaration *today*; under `defaults.unexported: package` it widened nothing. The fix is configuration-independent regardless: the enclosing directive fixes the scope the declaration would otherwise take, so `//declscope:private` under it binds under every configuration.
- **Not under a directive `loose` condemns.** Nothing under it is needed, the advice is to delete it, and a report per dependent would say the same thing N times.
- **Per anchor, not per name.** `a, b int` and `var x, y` share one insertion point, and the only directive that can narrow `b` narrows `a` too. The entry is reported only when every name in it is; a mixed entry is quiet, because a report on `b` alone could be cleared only by splitting the declaration, which is the author's call. Reporting it without a fix was the alternative, rejected because a boundary fix on the type would then leave that report behind (below). Each name still gets its own diagnostic, so the baseline and ignores name it; the first carries the one fix.
- **A type is judged with its members.** Narrowing a type narrows every member that states no scope, through containment. So a type is reported only when each such member is unexported and unreached as well, and then those members are not reported again: the type's fix settles them. They stay findings, marked with the type (`settledBy`), and `settledInReport` drops them only while the type's finding is not absorbed by the baseline. A baselined type offers no fix, so a member added to it later is new and must be reported. Regeneration records the members with the type for the same reason: the baseline it writes is what absorbs the type, and without them the next run would report the members it had just recorded the type for. An ignore needs no such test, since every ignore that silences the type is on the member's chain too. Narrowing a type over a reached member would start a boundary report, and over an exported one would narrow published API.
- **Interface method names are members and are judged too.** Satisfying the interface is not a use of the name, so an implementation elsewhere keeps nothing wide; a call from elsewhere does.
- **`main` in package main is exempt.** The toolchain finds it by name, and a directive on it says nothing.

The fix, and why it has guards `loose` does not need:

- **It breaks the line** when the declaration does not start one, through `directiveEditInReport`, the same insertion the boundary fix has always made for a field of a single-line struct. Withholding the fix there was considered and rejected: a boundary fix on a single-line struct would then leave an unfixable report behind.
- **A doc comment gets a bare `//` before the directive**, the house layout, unless it already ends in one or in a directive.
- **It is withheld when everything the enclosing directive decides for would be narrowed.** The directive would then bind nothing, the unused rule would report what `-fix` had just written, and under `loose` that rule has no fix. The case is real: an exported type whose directive exists only to widen unexported fields nobody reads. The advice there is to delete the directive, and the dependents are reported without a fix. A directive that already binds nothing withholds too, where narrowing under it would reword its unused report, and the advice there is the same deletion. `rewordedAtScopeSite` answers that by wording the report twice, before and after, rather than by asking which kind of directive it is: a block's report names each spec that takes its scope, a type's names the type and never a field, and a type that declares no name reads `taken` and, under strict, `overridden`, which a narrowed field flips. Withholding under every such directive is rejected: it leaves a type's field reported without a fix that would change nothing. `fixsurplusstrict/restated.go` pins a block withheld and a field offered, `fixsurplusstrictunusedstrict` an unnamed type withheld under strict, and `fixsurplusstrictunusedoff` that `unused: off` offers the fix, since no report is left to reword. `spec/surplus_strict.fsl` models it as `restated` and `rewords`.
- **Narrowing never makes `loose` fire.** A narrowed declaration was unreached and unexported, so it was never what kept the directive alive.
- **Fields are never reordered.** The house convention puts private fields last, but unkeyed composite literals, positional encodings, `unsafe.Offsetof` and 64-bit atomic alignment all observe order.

**Under `strict`, a boundary fix on a type narrows the members the widened type would leave wide, in the same edit** (`surplusNarrowedByTypeFix`). Without it the fix writes `//declscope:package` on an unexported type that took `private` from the default, the directive reaches every member, and each member no other namespace reads becomes a `strict` report the run did not start with — property 3 of `convergence_test.go`. The prediction reads the same evidence; an existing `//declscope:ignore surplus` on the member is consulted through `ignoreWouldSilence`, which **does not mark it used**, because nothing in this run is silenced by it and marking it would hide the unused-ignore report this run owes. Under `loose` nothing is narrowed: the type crosses, so its new directive is in use, and `loose` has nothing to say about it.

The two variants of a package with tests offer different boundary fixes for the same type — the non-test variant cannot see every file, so it narrows nothing — and the driver merges them: the type's insertion is identical, and the member insertions come from the test variant alone. The convergence test pins this with a `_test.go` file present.

There is no declaration-site rule for a method grown on another namespace's type. `checkBoundary` reports a method at its *declaration*, not at the call, so such a method is already caught wherever it is used — a declaration-site rule would only add a second diagnostic at the same position. The one case it would cover alone is a foreign method that is never called, which is dead code and an unused-code linter's business, the same reasoning that keeps "exported but unused outside the package" out of scope.

**Not being able to offer a rename is never a reason to stay silent.** An exported declaration is reported under `rules.naming.exported` even though no rename can ever be offered for it, and `checkQualify` reports even when its rename target is taken; keep new rules consistent with both.

**The naming rule reaches a foreign method, and only a foreign method.** A method is read through its receiver, which names the type's unit. That answers the ownership question while the method sits beside its type, and misdirects once it does not. `target.foreignMethod` compares the method's file with `ownerFile`, the file declaring the receiver's named type, and `named` lets the rule through only when they differ. A member, an interface method name and a method beside its type stay exempt.

This reverses the close of #59, which measured that foreign methods are almost always a type's methods filed by concern. That measurement was not disputed. The decision was that a receiver naming a unit which does not hold the method is a misdirection worth reporting, and the cost is real: 24 methods in this repository, 119 in suve. They were renamed rather than exempted, because a rule this repository does not hold itself to is one it should not ship.

The renames went to natural word order rather than a prefix: `addFuncToCollection`, `silencedByIgnore`, `bindAtScopeSite`. `c.site` could not become `ignoreSite`, which is already a type, and `siteOfIgnore` reads better anyway. `fileAt` moved to subject.go instead, since collect.go now asks it too and the core needs no prefix.


## Directives

| Directive | Level | Effect |
| --- | --- | --- |
| `//declscope:package` | Declaration or file | State the scope instead of deriving it from the defaults. On a type it also reaches the type's fields, not its methods; before the package clause it is the file's default, still overridable per declaration |
| `//declscope:private` | Declaration or file | Same |
| `//declscope:ignore` | Declaration or file | Silence every rule for the declaration, or for the whole file |
| `//declscope:ignore <rules>` | Declaration or file | Silence only the named rules (`boundary`, `qualify`, `surplus`, `unused`, `directive`, `filter`) |
| `//declscope:core` | File, before the package clause | Join the package's core namespace; conflicts with `//declscope:namespace` |
| `//declscope:namespace <name>` | File, before the package clause | Override the namespace derived from the file name |

**Only Go's canonical directive form is a directive.** `directive.split` hands the comment to `ast.ParseDirective` unchanged, after dropping a trailing `// reason`, so only `//declscope:name` (lowercase name, no spaces, line comment) is read. Any other comment whose body opens with `declscope:` is reported at every level, including `Stray`, with the one message `malformed declscope directive: write it as //declscope:name`, and takes no effect. Ignoring it would leave the author believing something is stated. Prose that mentions a directive does not open with `declscope:` and is never reported.

`parseIgnore` is shared by both levels, so `//declscope:ignore` cannot come to mean different things depending on where it is written. File-level directives live on `fileInfo.ignores`; declaration-level ones on `Decl.Ignores`. A file-level ignore is scoped to its **file**, not to its namespace, so files sharing a namespace each need their own — one file silently changing another's diagnostics would be much harder to trace back.

### The suppression chain

Scope resolution walks the same levels in the same order — the declaration, the containing type for a field, then the file the declaration is written in. The two chains share an **order**, not a rule: scope resolution takes the first hit, suppression consults all of them. Keep the order aligned when either changes.

`bind` marks a directive bound only when the scope it names is one the declaration could not have had under **any** configuration (`inert`, same file). That quantifier is why `rules.unused: loose`, the default, does not read `defaults.unexported`: comparing against it would change the judgment of every directive in the tree when one line of YAML changed, and would report a directive recording a deliberate `private`. `strict` is the opt-in that makes that comparison and accepts the trade (below).

### `rules.unused`

The unused rule carries every report that a directive decides nothing, and `rules.unused` takes `off`, `loose` or `strict`. The malformed, unknown, conflicting and misplaced reports are the `directive` rule's, which has **no key and is always on**: a directive that cannot be read leaves the author believing something is stated, and a switch that silenced those along with the unused ones would be the key that silences more than its name says. Keeping the two apart is what lets `off` exist. `off` reports no unused directive of any kind and offers no deletion; `reportUnusedScopeSites` and `reportUnusedIgnores` both return before judging anything.

`strict` makes the trade the quantifier above refuses, for a repository that wants every directive to change something today. **It is opt-in and `loose` is the default** for the reason `surplus` gives: an upgrade must not add reports to a repository whose config did not change, and under `strict` a change of `defaults.unexported` reports every directive restating the new default. `spec/unused_modes.fsl` is the model of the three modes.

- **The judgment reuses the resolution.** `redundantAtScopeSite` is called from `bindAtScopeSite` with the same chain, and asks `outerScopeOfScopeSite` what each stated level would give way to. It never resolves a scope a second way. `decided` stays `loose`'s answer, since `surplus` reads it.
- **It judges everything in reach, shadowed or not.** A nearer directive is judged against this one's scope today and against the level beyond once this one is deleted. The two must agree, or the deletion would flip the nearer one's judgment. `unusedstrict/a.go`'s `mixed` and the convergence cases pin it.
- **The chain puts back what a merge hid, for both modes.** `Decl.Merge` keeps the block's directive in `Beneath` when a spec states its own, and `bindAtScopeSite` walks it. Without it, a spec's `private` under a `package` block is judged against the file and called inert, and deleting it widens the spec. `unusedloose/b.go` and `c.go` pin both directions.
- **The message says what the declaration has, not where it comes from.** Deleting an outer directive in the same run moves the source, and a report the run keeps must read the same afterwards (property 3 of `convergence_test.go`).
- **Every reason is true of everything the directive reaches.** A declaration that took the other scope from a nearer directive is never said to have this one's. A block's report names only the specs that take its scope, or says that every spec states its own. A file-level report names nothing, so `messageOfScopeSite` reads `taken` and `overridden` to pick one of three reasons. A report that names nothing is not proof that nothing took the scope: a field of a type that declares no name (`type _ struct`) takes its type's scope and is never named, so an unnamed report is chosen by `taken` too, never by the names being empty. `unusedloose/d.go` and `unusedstrict/j.go` pin it. `overridden` is asked before `taken`, because a deletion in the same run can make a declaration a taker but never changes a scope. `unusedstrict/h.go`, `unusedstrict/i.go` and `unusedstrictpkg/b.go`, `c.go` pin each mix. Both modes share `messageOfScopeSite`, so a new reason is chosen in one place.
- **The fix is withheld where the deletion would move another report**, with the report kept: a taker of the directive's scope crossing (the boundary message names the level that decided), a field whose type the boundary fix widens in this run (`widened`, passed from `report`), a `//declscope:package` restating an enclosing one while `surplus` reads it (the declaration would join that directive's dependents, which `surplus: strict` judges), one under an ignore covering `surplus`, and one whose next level out is a directive that keeps its own report. That last one is a block: a spec joining it changes the specs its report names (`fixunusedstrictwithheld/d.go`), or, where `loose` alone reports it, turns "states its own scope" into a named report (`f.go`). An outer directive that an ignore answers is judged like any other. If it is redundant it stays redundant and answered after gaining the declaration; if it is not, `decide` refuses it, which keeps a bare ignore from being left answering nothing.
- **Only a pass that sees every file offers the fix**, like a rename. The ordinary variant of a package with in-package tests cannot see a crossing from a test file, and the driver applies what either variant offers, so the deletion the test variant withholds would be made anyway (`c.unseen(pass).all`). A file the build excludes is read for its names alone, so a taker it names counts as crossing. `spec/unused_modes.fsl` models both as `blind`.
- Every withholding reason has an in-process case in `fixunusedstrictwithheld`, `fixunusedstrictsurplus` or `TestSuggestedFixUnusedStrictUnseenTests` that fails when the reason is removed, and a convergence case that shows the report the fix would have changed.

declscope holds itself to `unused: strict` in `.declscope-strict.yaml`. Adopting it deleted six `//declscope:private` directives on unexported types in `internal/` (`ignoreSite`, `renameState`, `scopeSite`, `surplusDeclaration`, `surplusState`, and `scopesiteRemovals`). Each restated the default, and each type's fields that cross say so with their own `//declscope:package`, which binds with or without the type's.

`collection.silenced` walks the levels: the declaration, then, **for a field**, the type that owns it (`target.ownerObj`), then the file. It consults **all** of them rather than stopping at the first hit, and `ignored()` marks **every** directive covering the rule as used, so overlapping directives at different levels never make each other look unused.

Unused directives are therefore reported in a **second pass**, after every finding has been seen: a type's directive is often used up by a member reached later in the target list.

**Accounting is per physical directive, never per target.** `Decl.Merge` copies a block's ignore into every spec, and one `dir` is shared by every name in `var a, b` and `x, y int`, so a per-target "used" flag would judge one comment N times and report it unused whenever any sibling did not need it. `collection.ignores` keys an `ignoreSite` by the directive's position; `add` names every target the directive reaches on it, `ignored` marks the site used, and `reportUnusedIgnores` reports each unused site once, listing the declarations it was written for. Every declaration-level comment group goes through `collection.parseDecl`, which registers the site, records problems once per comment (so a bogus directive on a block is reported once, not once per spec), and marks the group **consumed** — see below.

**No ignore answers its own unused report.** That report is the unused rule's, so an ignore covering the rule could silence it, and one that silenced its own would never be called unused. So an ignore answers another's report and never the one at its own position (`ig.Pos != p.Pos` in `ignoreSilencesFile`, the same test on the siblings). Beside it on a declaration only an ignore **naming** `unused` answers; a bare one there would let a group of ignores exempt one another. At the file level a bare one answers too, since it stands every rule down for the file. An ignore that answers another's report is used, and `reportUnusedIgnores` settles every answer over the sites that silenced nothing **before** any report is made, so the result does not depend on the order the sites are judged in: the file-level filter that runs afterwards would otherwise find the answerer unused a moment before it did its job. `spec/unused_ignore.fsl` is the model, and `testdata/src/ignoreunused` and `ignoredirective` pin each case, including a leftover `//declscope:ignore directive` reported beside the unused scope directive it was written for.

**Only a pass that sees every reference may call a directive unused.** The ordinary variant of a package with in-package `_test.go` files cannot see the references those files make, so a directive needed only by a test would be reported unused there and reported necessary by the test variant. `reportUnusedIgnores` returns early when `hasUnseenTests` holds — the same predicate that withholds renames, kept on `collection` because both features ask it — and defers to the test variant, on exactly the reasoning that keeps unmatched baseline entries unreported (below). A more permissive rule — report in the ordinary variant unless the test variant *could* need it — would mean parsing the sibling test files for references, which is the heuristic path the rename guard also rejects.

> [!NOTE]
> The consequence, documented in the README, is that `-test=false` yields no unused-ignore report for packages with in-package tests.

Two reports live here and must not be conflated. **Misplaced** is structural: go/parser attached the comment to no node. **Unused** is about reach: the directive is attached correctly but no scope in its reach comes from it (`spec/unused_bind.fsl`). Under `loose` that test is deliberately structural rather than semantic — asking whether the scope *differs* from the one already in force would make recording a deliberate `private` an error, and would turn one line of `.declscope.yaml` into hundreds of diagnostics in untouched files. `strict` asks exactly that, and only when the repository opts in.

**A directive that binds to nothing is reported as misplaced, never dropped.** go/parser attaches a comment such as the one in `type X struct { //declscope:ignore boundary` to nothing, so the contract has two halves. Binding: `looseTrailing` finds an unattached comment trailing a node's **first or last line**, and `addFunc`, `addGenDecl` (for the block's own `(`/`)` lines) and `specGroups` read it; `attached` lists the groups the parser did hang on something inside the node, which win, so a field's trailing comment on the brace line stays the field's — and `specGroups` parses only the spec's *own* Doc/Comment plus the loose groups, never the fields', because feeding the fields' groups into the type's parse lands a field's `//declscope:package` on the type (the convergence test catches this). Reporting: `collection.stray` walks every comment group after the package clause that `parseDecl` never consumed and reports each directive in it through `directive.Stray`. The first-or-last-line rule is deliberately blunt: a directive on a middle line of a multi-line signature or struct is misplaced, because the alternative is guessing which declaration a comment "near" one belongs to.

### Placement

`//declscope:namespace` matches Go's directive syntax, so `go/doc` strips it from rendered documentation. In a file with a package comment it belongs at the bottom of that comment after a blank `//` line; in a file without one it is separated from the package clause by a blank line, because flush against `package` it becomes an empty package comment and adds a stray blank line to the rendered package doc. `directive.ParseFile` scans `file.Comments` rather than `file.Doc`, so every placement is recognized.

Declaration-level directives go in a declaration's doc comment, or in a trailing comment on its first or last line. `ast.FuncDecl` has no `Comment` field, and no node owns a comment after an opening brace or parenthesis, so those are found through `fileInfo.lineComments` (`looseTrailing`). A directive on a parenthesized block applies to every spec in it, and `directive.Decl.Merge` layers the spec's own over it: a scope directive on the spec replaces the block's, while ignores accumulate. The union is deliberate — a narrower ignore must not silently re-enable a rule the block turned off — and `testdata/src/ignorescope` pins it, so keep the docs and that test in step. The one exception is the `unused` rule: its report is about a directive, not a declaration, so a block's or a type's ignore does not answer an unused report on a spec or field inside it. Only an ignore on the same declaration, or at file level, does. Otherwise one ignore on a block would hide every stale directive under it.

Unused ignore directives are reported, matching the convention in `mpyw/gormreuse` and `mpyw/zerologlintctx`. Ignores are consulted **before** the baseline, so a suppression the baseline would also have absorbed still counts as the directive doing its job.

## Suggested fixes

Every diagnostic carries **at most one** fix, which is what makes `-fix` unambiguous:

- A boundary crossing is fixed by inserting `//declscope:package`.
- A missing prefix is fixed by renaming.

They can never conflict, because a rename does not change reach. (`x/tools`' `ApplyFixes` applies only the first fix of a diagnostic and logs `ignoring alternative fix` for the rest, so carrying alternatives is a liability.)

**Two fixes in one run can still converge, and each way has a guard.** Every fix is decided against the pre-fix source and none of them can see the others. For renames that is `reserved` (below) and `spec/rename_siblings.fsl`. For directive insertions it is `subsumedByReport`: a directive written on a type reaches the type's members, so a member fixed in the same run was left carrying one that bound nothing, and the `unused` rule reported what `-fix` had just written. The wider insertion wins and the member's is dropped; **the member's diagnostic is not**, because the crossing is real until the type's directive lands. `spec/fix_members.fsl` proves it, and `testdata/src/fixmembers` pins that a member whose type does not cross still gets its own fix.

The decision cannot be taken while reporting one target at a time, which is why `report` collects every surviving finding first. Ordering the targets instead would only decide which of the two fixes is written, never whether both are.

There is no equivalent for a `var`/`const`/`type` block. A fix is anchored on the spec, never on the block, so two specs each get their own directive and each one binds.

### Why the rename fix withholds

**A rename is offered only when it is provably safe** (`renameSafe` in `internal/rename.go`); the diagnostic is reported either way. A guard that checks only `pass.Pkg.Scope().Lookup(newName)` produces code that does not compile or, worse, compiles into a program computing something else: Go resolves a name from the inside out, so `var count` renamed to `fooCount` inside `func Add(fooCount int) int { return fooCount + count }` silently becomes `fooCount + fooCount`. A full renamer is rejected in favor of withholding; a withheld fix costs one manual edit, a wrong one is a bug the linter cannot see. `spec/rename_sound.fsl` and `spec/rename_siblings.fsl` model the resolution order and the sibling collision.

The conditions, each conservative:

- The new name is not in package scope, not predeclared (`types.Universe`), and not bound in **any** file scope (`fileScopesBind`) — Go rejects a package-level name that any file imports, so this cannot be limited to files with references. The predeclared check is unreachable through `qualify` today, whose target always contains an uppercase letter; it stays because `renameSafe` is a contract independent of its caller, and `rename_sound.fsl` proves a guard without it is unsound.
- At every ident naming the object, `pass.Pkg.Scope().Innermost(pos).LookupParent(newName, pos)` finds nothing. This catches parameters, named results, locals declared before the reference, closure parameters, range variables, type parameters, receivers, the same file's imports and the universe; it correctly ignores locals declared after the reference, field names and prefixes; and it does **not** see another file's imports, which is why the file-scope check above is separate.
- The object is not named from a file the pass did not collect (generated or filtered out), since those are never rewritten (`usedOutside`, normalized the same way as `collectRefs`).
- No `//go:linkname` or `//export` in the package names the object as text.
- No earlier fix in the same pass has claimed the name (`reserved`). Fixes are generated from one pre-fix state and cannot see each other; `Qualify` is not injective across namespaces (`a.go`'s `bX` and `a_b.go`'s `x` both prefix to `aBX`), so two declarations can target one name. Reservation makes the **order** of targets load-bearing, which is why `report` sorts by (file name, offset) rather than `token.Pos`: go/packages parses files concurrently, so the order files enter the FileSet differs between runs, and sorting by `Pos` would make a different sibling win in the `-json` run than in the `-fix` run.
- The package has no in-package `_test.go` files that this pass does not see (`hasUnseenTests`, a directory listing plus `parser.PackageClauseOnly`). The non-test variant cannot see what test files declare or use, so it withholds every rename and defers to the test variant, which sees every file and whose fix rewrites the non-test files too. The driver coalesces identical edits from both variants, so with `-test` on (the default) nothing is lost; with `-test=false`, packages with tests get no rename fix. Parsing the sibling test files to summarize what they spell, import and would themselves be renamed to would be more permissive but heuristic (an unaliased import's name is only known by loading it); the blunt rule is the one that is provably consistent between the two variants.

Renames are also never offered for members. A namespace that cannot be a prefix at all (`namespace.CanPrefix` is false) produces no naming diagnostic in the first place, rather than a diagnostic without a rename.

**A declaration whose own directive states its scope gets no fix** — `t.dir.HasScope` must consult the declaration level only. Both that directive and the use site are deliberate, so `-fix` must not overwrite the author's decision. A scope inherited from the containing type or from the file is a *default*, and the fix overrides it: the inserted directive sits on the declaration, which outranks both, so it states an exception rather than overwriting anything. `spec/boundary_fix.fsl`'s `FixOverridesTypeAndFile` pins that, and its `trans` guards pin that no fix is offered where no violation exists.

`directiveFix` checks whether the anchor starts its line (`startsLine`, via `pass.ReadFile`). A field of a single-line struct does not, and inserting the directive there would attach it to the `struct {` line instead of the field.

## Baseline

`declscope baseline ./...` regenerates baseline files wholesale; they are never hand-edited. Entries are keyed by (package, rule, declaration) — deliberately not by position — so they survive code motion and file renames.

Generation does not go through `singlechecker`: a baseline entry has to identify a violation structurally, and a driver only returns rendered diagnostics. The analyzer declares no `Requires` and exports no facts, so `cmd/declscope/baseline.go` drives it over `go/packages` with a hand-built `analysis.Pass`, calling `internal.Collect`. Keep that entry point working if the analyzer ever gains dependencies.

`baseline` and `survey` analyze their packages in parallel through `loadInParallel` (`cmd/declscope/load.go`), and `inspect` analyzes one package, so it has nothing to spread. Each package's config is resolved and analyzed into its own slot, and the slots are folded **in package order** afterwards. That is what keeps the output byte-identical to a sequential run and the first error the one a sequential run would stop at, with no lock anywhere. Do not fold as results arrive. The analysis is safe to run concurrently because `singlechecker` already does. The gain depends on how much of the run is analysis rather than loading: over the standard library it cut `baseline` from 2.89s to 2.20s and `survey` from 2.60s to 2.27s, and over suve, where loading dominates, it changed almost nothing.

**The target is resolved per package, on the analyzer's lookup path.** The analyzer finds a baseline from each package's own directory (`config.Resolve`: the file the nearest config names, else `FindBaseline`'s upward search for a default-named file), so a baseline only suppresses what is written where that lookup ends. Resolving one output path from the working directory and pouring every package into it would leave a subtree with its own configured or default-named baseline reporting forever. `collect` therefore groups keys by target:

| Situation | Where the package's entries go |
| --- | --- |
| `-o <file>` given | That one file, for every package |
| The nearest config names a baseline | The named file, resolved against the config (`config.ResolveForBaseline`) |
| A default-named file exists between the package and the working directory | The nearest such file (`config.DefaultBaseline`) |
| Otherwise, and the walk reaches the working directory | A new `.declscope-baseline.yaml` in the working directory |
| The walk never reaches the working directory | The whole run refuses, naming the packages |

`config.DefaultBaseline` walks the same path as `FindBaseline` but **stops at the working directory**. Stopping there is what makes the README's "the working directory" true and prevents data loss: an upward search from a subdirectory would find the module-root baseline and rewrite it with only that subtree's entries. A file above cwd is left alone; a new file in cwd shadows it for exactly the packages under cwd. A package whose lookup never reaches cwd (another module in a workspace, or a directory outside it) makes the whole run refuse, because a file written in cwd would never be found from there. `-o` bypasses all of this and gathers everything into one file. Refusing whenever packages disagree is the alternative; it would make the documented "its presence is all it takes" depend on the layout instead of holding.

**Regeneration never loads the existing baseline.** Loading happens in `config.Resolve`, which analysis uses; `config.ResolveForBaseline` applies the same config and hands the configured path back without reading it, and `Options.Compile` does not load it either. Otherwise a baseline that fails to parse would block its own regeneration — the one remedy the documentation offers. `baseline.Save` returns the number of entries written, after deduplication, and that is the count the subcommand reports: a package and its test variant hand over the same key twice.

The analyzer deliberately does **not** report unmatched baseline entries. A package's test variant sees references the ordinary variant does not, so an entry that matched nothing in one pass is not evidence it is stale. Regeneration is what prunes, and its diff is the record of what was fixed.

## Testing

```bash
go test ./...          # analysistest + unit tests
./coverage.sh          # the same tests, printing the merged coverage per package
mise x -- ./test_all.sh   # tests with coverage, golangci-lint, dogfooding and the specs
```

- `testdata/src/*` are `analysistest` packages. Most carry their own `.declscope.yaml`, which also exercises config discovery end to end — the naming rule is off by default, so every package asserting qualify behavior (including the unused-ignore accounting for it) has to state `qualify: ondemand` or `always`. `qualifydefault/` deliberately carries none: it pins the default itself.
- Goldens are plain files, not txtar archives, because no diagnostic carries alternative fixes.
- `convergence_test.go` applies `-fix` through the real binary in **one** pass and checks that the result type-checks, that every diagnostic which offered a fix is gone, and that no diagnostic appeared that was not there before. It type-checks with `go vet`, not `go build`, because vet also compiles the test variant — a rename applied to the non-test files alone builds and then fails the first `go test`. Keep it to one pass: repeating it would hide a fix that only works the second time. Each way a rename can be unsafe has a case there, arranged so that the wrong rename fails to type-check (a captured parameter is given a type the expression rejects), since the test cannot run the result.
- `testdata/src/fix*` pin where a fix is offered and where it is withheld. `RunWithSuggestedFixes` compares a golden only for files that received edits, so a package that tests withholding also carries one declaration that *is* renamed: a wrongly offered fix then fails for want of a golden, and the golden shows the guard is precise rather than merely off.
- Keep each testdata package focused on one rule. `qualifyrule/order.go` deliberately touches nothing in namespace `user`, so the naming rule is tested without boundary diagnostics landing on the same lines.
- Diagnostics on directives are reported at the comment, so their `// want` comments belong on the directive line, not the declaration line.
- `analysistest` analyzes **both** variants of a package with `_test.go` files and checks every `// want` in each, so a `want` in a non-test file must hold in both. A diagnostic that only the test variant reports can be pinned only from inside a `_test.go` file, which the ordinary variant never checks; `testdata/src/testonlyignore` is shaped that way. Deferral itself is pinned by the *absence* of a report.
- `testdata/src/blockignore`, `testonlyignore` and `braceignore` pin the three halves of the unused-directive contract (one comment judged once; only a complete pass judges; a directive binds on its first or last line or is reported misplaced). A sink like `var _ = userE` written in another namespace is a cross-namespace **reference** and will use up the very directive the test means to show unused — keep sinks in the declaring file.
- `testdata/src/baselined` carries its own `.declscope-baseline.yaml`, which also exercises the lookup end to end.
- `testdata/src/surplusstrict*` pin `strict` one suppressor per package, the way `surplus*` do for `loose`, and each states `surplus: strict` since the default is `loose`. `surplusloose` pins that the default leaves a dependent of a directive in use alone. `surplusstricttests` pins a report only the test variant makes from inside a `_test.go` file. `fixsurplusstrict/dto.go` takes no edit and has no golden on purpose: it is the withheld case, and a wrongly offered fix fails for want of one.
- `testdata/src/unusedloose` pins that the default keeps a directive naming today's default, `unusedoff` that `off` reports no unused directive while the `directive` rule still reports, and `unusedstrict` and `unusedstrictpkg` pin `strict` under each default. `unusedstrict` states `surplus: off`, since surplus would report the `//declscope:package` directives it keeps. `fixunusedstrict/b.go` takes no edit and has no golden on purpose: it is the withheld crossing case. `fixunusedstrictwithheld` (under `surplus: off`) and `fixunusedstrictsurplus` (under `defaults.unexported: package`) hold one withholding reason per file, and only the files a fix edits have goldens. `unusedstricttests` is read by `TestSuggestedFixUnusedStrictUnseenTests` rather than through `want` comments, since its boundary report exists in the test variant alone. The goldens compare after gofmt, so the bytes the deletion leaves (the `//` separator, blank lines, CRLF) are pinned by `TestScopesiteRemoval` in `internal/scopesite_test.go`.
- `internal/shrink/testdata/*` are whole modules, each with its own `go.mod`, since `shrink` loads a module rather than a package. A module zip leaves out any directory holding a `go.mod`, so they never ship. Expectations are `// want: <regexp>` comments on the reported line, matched against the message, one per line. `TestShrinkConverges` applies every fix to a copy and runs `go vet -composites=false`, which also compiles the tests. `composites` is off because `edge` writes another package's struct unkeyed on purpose.
- `testdata/src/braceignore/user.go` is deliberately not gofmt-clean; it is fixture data for comment placement, so exclude it when checking `gofmt -l .`.

### Coverage

The subcommand tests drive the **built binary** as a subprocess, because what they assert is the handshake between a subcommand and the analyzer. `go test -coverprofile` therefore counts none of the statements they run, and `cmd/declscope` read as 1% covered while being the most thoroughly exercised package in the tree.

`DECLSCOPE_COVERDIR` closes that without turning the tests into unit tests of halves: `cmd/declscope/cover_test.go` builds the binary with `go build -cover` and points every run at that directory. `coverage.sh` sets it, converts what lands there with `go tool covdata textfmt`, merges it with `go test`'s profile into `coverage-merged.txt`, and prints the coverage per package. `test_all.sh` and CI both run it, and CI uploads the merged profile. It passes `-count=1`: a cached package runs no test and starts no binary, so a second run read `cmd/declscope` as 1.2% covered. The cache could not save anything anyway, since the counters are needed from every run. Name the directory by an **absolute** path — `go test` runs each test binary in its own package directory. Without the variable the binary is built and run exactly as before, so a plain `go test ./...` pays nothing for it.

`convergence_test.go` builds its own binary without `-cover`, so what it runs counts nowhere. A path only it reaches needs an analysistest fixture too, as `fixsurplusnarrow` is for the members a type fix narrows.

The statements left uncovered are defensive: I/O errors (`os.Executable`, `os.Getwd`, `filepath.Abs`, a directory that cannot be read, a write to stdout), go/types and go/parser contracts (a nil field list, a method with no receiver type, a position in no collected file), the yaml encoder failing on a struct of strings, a cgo file a driver shows unprocessed, the go command's older `_testmain.go` answer, and the rename guards `renameSafe` keeps as a contract independent of its caller. Anything else uncovered is a missing test or dead code.

`codecov.yml` therefore excludes nothing. `main.go` was excluded while no test could reach it; with the counters it is covered like the rest, and an ignore list nothing needs is one that quietly grows.

> [!WARNING]
> Do not add a `.declscope.yaml` or `.declscope-baseline.yaml` at the repository root. Both are found by an upward lookup from each analyzed package, so a default-named file at the root would reach every `testdata` package and change what the tests assert. The settings declscope holds itself to live in `.declscope-strict.yaml` and are applied with an explicit `-config` in CI and `test_all.sh`.

### Formal specs

`spec/*.fsl` are machine-checked models of the rules, the configuration space and the rename guard; `spec/README.md` lists what each proves and the exact `fslc` commands and depths. `spec/verify.sh` runs them — every spec named in its `proving` list must be `proved` under induction, and two must stay `violated` — and is wired into `test_all.sh` and a CI job. Documentation that nothing re-runs is documentation that drifts.

> [!CAUTION]
> `fslc verify` is a bounded model checker that holds the whole reachable state space in memory. A spec that models the full product in one action with many parameters needs gigabytes for the same claims the split specs prove in single-digit megabytes. Keep each spec to the variables its own properties read, keep the depths given in `spec/README.md`, and do not run `fslc verify` on a machine that cannot spare the memory.

## Documentation site

The GitHub Pages site is generated from `README.md` and `docs/`, the same way as `mpyw/suve`; nothing generated is committed. `.github/scripts/build-docs-site.py` splits the README into one page per `##` section and rewrites every `#anchor` to the page it landed on, MkDocs Material builds it with `--strict`, and `check-site-links.py` validates the rendered HTML. `.github/workflows/pages.yml` runs all three on every PR that touches them and deploys from `main`. `mise run docs-build` runs the same steps locally, and `mise run docs-serve` previews the site.

- **The build fails rather than ship a broken link.** An unmapped anchor, a missing asset, or a README link to a repository file that does not exist is an error. A README link to a file the site does not carry (`skills/…/SKILL.md`) is rewritten to that file on GitHub.
- **Keep headings unique when they are linked.** A `#anchor` whose slug occurs on two headings is ambiguous after the split and fails the build.
- **`<!-- site:skip -->` … `<!-- /site:skip -->` is GitHub-only.** The README's link to the site sits in one, since it would point at itself there.
- **The logo is drawn on a 16×16 grid** (`docs/assets/logo*.svg`) so that the favicon stays sharp at 16px. `logo-light.svg` is for a light background, `logo-dark.svg` for a dark one, and `logo.svg` switches between them by `prefers-color-scheme`. Keep new coordinates on whole units.
- **`docs/assets/social-preview.png` is captured from `social-preview.html`** at 1280×640 in a headless browser. Edit the HTML and capture again rather than editing the PNG. GitHub's own social preview is uploaded by hand in the repository settings, so it has to be uploaded again after a change.

## Conventions

- Module: `github.com/mpyw/declscope`, matching the layout of `mpyw/gormreuse` and `mpyw/zerologlintctx`.
- `go.mod` pins `toolchain go1.27.0` while keeping the `go` directive at 1.25.0, because golangci-lint refuses to load a module whose `go` directive is newer than the Go it was built with.
  The pin governs builds made inside this module, including the release build. It does not reach `go install pkg@version` or `go run pkg@version`, which ignore a dependency module's `toolchain` directive and treat its `go` directive as a lower bound only, so those commands build declscope with the user's own `go` release.
- Distribution is via GitHub Releases (goreleaser) with **mise as the recommended install path**; `go install` / `go tool` / `go vet -vettool` also work.
- `-V=full` is answered by `cmd/declscope/version.go`, not by `x/tools`, whose `addVersionFlag` hardcodes `devel` and is skipped when a `-V` is already registered. Releases stamp `-X main.version` from `.goreleaser.yaml`; `go install pkg@v` reaches no linker flag, so `debug.ReadBuildInfo` is the fallback. Keep the printed line in the shape the go command's tool-ID protocol reads: `<progname> version <version> ... buildID=<id>`, with the buildID last so a `devel` binary still identifies itself.
